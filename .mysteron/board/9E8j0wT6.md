**Gap.** When a `mysteron join` guest loses its WebSocket connection to the host (network blip, host restart, sleep/wake cycle), the guest process just stops. The user has to re-run `mysteron join` manually. For the "distributed fleet working while you sleep" use case, a dropped connection shouldn't require manual intervention.

**Fix.** In `src/worker/guest.ts`, wrap the connection lifecycle with an auto-reconnect loop:

1. **Detect disconnect.** On WebSocket `close` or `error`, instead of exiting, enter a retry loop.
2. **Exponential backoff.** Delay before reconnecting: 2s → 4s → 8s → 16s → 30s (capped). Add ±20% jitter.
3. **Respect `--for` duration.** Only reconnect if the original offer's expiry time hasn't passed. If the offer expires while offline, exit cleanly.
4. **No mid-run reconnect.** If a run is actively in flight when the connection drops, the run completes in the throwaway repo normally (it doesn't need the WebSocket for agent execution). The diff is returned on reconnect, or stored locally if the reconnect never succeeds.
5. **TUI feedback.** The `GuestTui` (`src/worker/guest-tui.ts`) already shows a connection badge — show a "reconnecting (attempt N, next in Xs)" state.
6. **`--no-reconnect` flag.** Allow opting out of auto-reconnect for scripting contexts where you want a clean exit on disconnect.

**Implementation notes:**
- The reconnect loop should use the same token. Tokens don't expire (they're revoked by the host), so reconnecting with the same token should work as long as the host still accepts it.
- Log each reconnect attempt with timestamp so the TUI shows progress.
- Test: simulate a close event, assert the guest re-attempts connection up to N times before giving up.

**Acceptance.** Killing and restarting the host while a guest is connected results in the guest automatically reconnecting within 30 seconds, without user intervention, as long as the `--for` window hasn't expired.
